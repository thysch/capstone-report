1. Abstract

Semiconductor handlers are complex and expensive machines that move devices through various test beds into categorized output trays. In order to fully explore the design space of building these machines, a configurable simulation, or digital twin, can provide key insights into how changes in the machine configuration affect the total throughput.

The objective of this project is to create a configurable simulation of a pick and place semiconductor handler. The simulation should be easy to configure for new users while allowing more advanced users fine control over all aspects of the simulation.

The technology stack will utilize JSON files, C#, and GDScript to simulate and visualize the semiconductor handler within Godot. The simulation will also support an exposed programming interface, or API, so that the simulation can be interacted with through scripting or IPC in future releases.

The main architecture of the program will be a layered architecture. The bottom layer is the model or simulation layer, which is composed of the data configuration files and the simulation timing and math. The User Interface layer is composed of the UI which includes buttons, various user interface windows, and the visual simulation.  The glue binding these layers together is the ViewModel, which will expose the output values of the simulation layer and passively update the View to reflect changes to the simulation.

It is our hope that by leveraging the C# and scripting capabilities of Godot, we can create a user-friendly and powerful simulation tool that will help in the process of semiconductor handler design.

3.  Problem Statement

The development and validation of automated test handlers can require extensive physical prototyping. This approach can be expensive, time-intensive, and prone to operational disruption. In automated test handlers, the interactions between pick and place handlers, software packages, trays, heat treatment, transport mechanisms and testing stations create complex behaviors that can be difficult to analyze through physical testing alone. This Capstone project aims to create a digital twin of automated test handler systems capable of simulating machine operations, visualizing system state and supporting performance analysis.  This digital twin system will provide a safe and configurable environment for validating machine designs, evaluating processes, and improving system workflows before real-world implementation.

3.1 Business Background

Semiconductor test handlers are large, expensive, and complex machines that use pick and place heads to move devices through trays and various test beds. The throughput of these machines depends on many interacting factors such as component dimensions, motion profiles, and optimization strategies. Testing new handler configurations on real hardware is a slow and expensive process. Engineers and operators lack an accessible and configurable simulation that can calculate UPH and other related metrics.

Semiconductor test handlers often work with semiconductor packages such as integrated circuits that are tested during manufacturing using automated equipment known as test handlers.

A test handler is a highly automated machine that transports semiconductor packages

through a sequence of operations. Depending on the machine configuration, these

operations may include:

  • Loading devices from trays or other input media;
  • Positioning and orienting devices;
  • Optical inspection;
  • Temperature conditioning;
  • Electrical testing;
  • Sorting devices according to test results;
  • Placing devices into output or reject locations.

Modern test handlers contain multiple mechanical mechanisms operating concurrently,

including pick-and-place heads, shuttles, elevators, trays, test sites, storage buffers, and

inspection stations.

Understanding the operation and material flow through these machines can be challenging

because several semiconductor devices may be moving or processing simultaneously in

different areas of the machine.

3.2 Needs

The sponsor would like to investigate a software-based Test Handler Visualizer and Simulator that

provides a graphical representation of the machine while also executing a simplified simulation of its operation. This is known as the digital twin platform to create digital representatives of the physical machines and it is commonly used within industrial manufacturing. The digital twin platform is needed by the sponsor and other companies as a method to help reduce unplanned downtime by allowing them to test for failure and inefficiencies. It also allows companies to accelerate various configurations to market by allowing them to utilize the digital platform before committing to the physical setup of their machines. Companies will want to optimize their operational efficiency by testing various configurations without disrupting their physical or real-life operations. This leads to the next need that many companies wish to reduce waste in their operational testing. A digital twin will allow companies to avoid physical testing and reduce wear on their physical machines. With the cost of prototyping reduced by digital twin platforms, it allows companies to gather data needed to make informed decisions on how they would like to set up their machines in the physical realm. This will allow companies like the sponsor and their prospective customers to have data-driven decisions that can benefit them with a number of advantages.

3.3 Objectives

The objective of this project is to design and develop a prototype software application that visually represents the operation of a semiconductor test handler and simulates the

movement and processing of semiconductor packages through the machine.

The application should represent:

  • Semiconductor packages;
  • Storage locations;
  • Processing stations;
  • Pick-and-place and transport mechanisms;
  • Material-flow paths;
  • Machine states;
  • Package movement through the machine.

Behind the visualization, the application shall contain a simplified simulation engine

responsible for maintaining the logical state of the machine and moving semiconductor

packages between stations.

The simulation shall be controllable through both the graphical user interface and defined

software APIs.

The resulting prototype should demonstrate how a configurable visualization and

simulation framework could be used to represent multiple types of semiconductor test

handlers.

4.1.1 Glossary of Relevant Domain Language

App Settings Configuration File

The configuration JSON file which contains machine independent user settings for the application.

Crackle

The change in Snap over time (5th derivative of position).

Handler Component

An individual, primary component of the semiconductor handler such as the Pick and Place Handler, Shuttle, or Test Site.

Jerk

The change in acceleration over time (3rd derivative of position).

Machine Recipe Configuration File

The machine-specific configuration JSON file which is used to define the custom configuration of a semiconductor handler.

Motion Profile

A description of the change in position, velocity, or acceleration over time which defines how a mechanical component moves linearly.

Nozzle

The component which is attached to the pick and place head. It is used to pick up and place devices using controlled suction. Multiple nozzles may be used in conjunction for larger devices.

Pick and Place Handler

A 2-axis gantry system which is used to move the pick and place head in order to transport semiconductor devices throughout the machine.

Pick and Place Head

The component which is moved by the X and Y axes of the pick and place handler. Typically has an array of 4x2 nozzles which can change its pitch and extend and retract vertically at some stroke.

Pocket

A depression in some component which is designed to hold a semiconductor device of a certain size.

Pop

The change in Crackle over time (6th derivative of position).

Semiconductor Device (aka “Chip”)

The components which are processed by the semiconductor handler. Each device is typically a rectangular chip in the range of 3 x 3 mm to 110 x 110 mm, with heights ranging from 1 mm to 22 mm.

Semiconductor Handler (aka “Machine”)

The top-level machine which tests and sorts semiconductor devices.

Snap

The change in Jerk over time (4th derivative of position).

Testing Station

A component of the semiconductor handler which is used to test devices using visual inspection or electrical testing.

Tray

A flat plastic rectangular block with shallow pockets which holds the semiconductor devices. Used for input of components and output sorting.

5. Exploratory Studies

5.1 Relevant Development Frameworks

Framework Exploration:
        Our main concern would be having a cross-platform application that would work on MacOS, Linux and Windows 11 as each member of our development team all work on different operating systems. We also had to consider a graphical engine that would work under the same cross-platform requirement. This cross-platform vastly reduced our selection pool as the Sponsor’s proposal had a list of available recommended technology stack. Most of the recommended technology was primarily for enterprise level software, which gravitated toward Windows OS only applications. The graphical UI and game engine was impacted by our internal team requirement so our choice was really to go with Avalonia with Silk.net, or Avalonia with Godot.

Our first prototype was done to figure which UI and graphical technology stack would work well with our cross-platform requirement. We had attempted to use Avalonia purely as both UI and graphical output. However, we found the Avalonia was limited in its graphical functionality to be limited in its animation. The first real combination was using Avalonia with Silk.net, which proved to be successful. The major downside with using Silk .net was the significant involvement of having to design our graphical models of the system. Therefore, we tried another combination of Avalonia and Godot that we found to be feasible; but, it had one major caveat in that we had to separate the game engine from the Avalonia and we could not embed Godot within Avalonia.  

Our next prototype ended up using Godot as both UI and graphical engine for our simulation, which worked out quite well. We are still testing many different functions and we were also able to establish a link between our machine model and the graphical interfaces that Godot allows us to use C# and .Net for much of our machine model and event handling. This allows us the benefit to keep our visual and logical layer seperate. We are currently seeking more information from prototyping for this setup using GDScript for most of our UI and graphical layers and C# for the machine model. We mainly need to ensure that Godot can provide the same level of UI controls that Avalonia has once performed.

Main Development tools:

5.2 Relevant Solution Techniques

Choice to use Godot

        Godot is an open source game engine that is available to multiple operating systems and it uses the MIT license. The MIT license is well suited for enterprise software development as it does not require us to open-source our final product and enables the sponsor to maintain its proprietary information from the public. The major benefit is that we have no copyleft obligation and we can modify and use their software within our application without having to release our code. Another benefit is that we are also allowed to sell, sublicense and distribute our software application with Godot. The only major limitation is that we must include the original copyright notice for using Godot, and we are also not able to obtain a patent under this license.  Another limitation is the small legal issue that the sponsor will also need to review this license to ensure it does not interfere with their objectives for this project.

        We can mitigate any issues with using Godot by ensuring that most of our software application is developed in C# and only having critical UI and graphical elements coded in GDScript. This should allow the sponsor if they choose to go with a different UI or graphical technology option if they find Godot or its MIT license to be insufficient for their needs. Earlier, our team had wanted to build the entire development using purely GDscript, which could be a problem for an enterprise company who may seek an alternative for their needs. It should be imperative that we keep the most of our software in C# to allow the sponsor the freedom to choose new UI and graphical elements once the project is completed.

        Some of the useful features found in Godot is the GDExtension that allow developers to integrate external libraries specifically targeting C++ and C# languages that are prevalent in game development. Godot uses a hierarchy of nodes which can be attached to classes within the C# libraries and files. This provides a useful interface between GDScript and C# for developers to utilize. The only downside is that development will be split between C# and GDScript. Godot is also flexible in that it does not limit us to GDscript language within their development process. Godot IDE offers a C# version that allows developments to use C# instead of GDScript if they prefer using a singular language across the entire development.
        Godot's graphics engine uses either OpenGL, Direct3d, or Vulkan that enables it to be cross-platform compatible with many different operating systems and it includes some mobile OS’s as well. Another major feature of the game engine is that it offers an in-house physics engine that should allow us to create physics based animation sequences if we decide it is appropriate to do so.

GDScript is a built-in language specifically for Godot and it is a high level language that is similar to Python. It is also a gradually typed programming language that allows for static and dynamic types. Its C++ backend can apply optimizations that can increase its performance significantly. For long-term prospects, its language is still under support by the maintainers and we should expect continued support in the long-term.

Required Algorithms

Several algorithms will be necessary for the simulation layer of this project including Pick Algorithms and Motion Profiles. Pick algorithms will be used to determine which chips the pick and place head will pick up when it travels to the input tray, as well as how chips are placed in output trays. Possible pick algorithms include Row Scan, Nearest Neighbor, or Clustering. These algorithms will be abstracted for the user, with custom algorithm scripting as an option for more advanced users. If our pick algorithms are advanced enough, they may provide additional functionality to the handler such as the option to continue operation even if one of the 8 nozzles fails.

Motion profiles required for this project will describe how a linear axis is traversed based on position, velocity, and acceleration. Possible motion profiles include Trapezoidal, S-curve (See Figure 5), or Snap-based motion profiles. Trapezoidal is typically the fastest motion profile, while S-curve and Snap-based introduce limits on an object’s acceleration to avoid sudden jerks which can damage components. Similar to the pick algorithms, we plan to abstract these profiles for users while providing scripting capabilities for more advanced users.

Motion profiles will be defined using industry standard motion algorithms such as limiting Jerk or Snap. Jerk is defined as the change in acceleration over time while Snap is defined as the change in Jerk over time ². By defining motion profiles based on these factors, we can reduce the risk of damaging components ³. We may also include the possibility of asymmetrical motion profiles and a visual editor to define custom motion profiles for advanced users who do not want to use scripting.  

Figure 5 - Example of an S-curve motion profile.

Another related feature to motion profiles is movement blending. This will allow users to configure the timings of when movements are executed in order to optimize the cycle time. For example the pick and place nozzles might be able to begin moving vertically 50 ms before the pick and place head reaches its XY horizontal destination, which can save cycle time and increase UPH.  Similarly, options such as Edge-Pick might allow users to configure picking up a chip from the closest corner to the Pick and Place head’s current location, rather than always picking up a chip from the center.

7. System Implementation

7.1 Programming Languages & Tools

We plan to use a combination of C# and GDScript within Godot to create the digital twin. C# will be used for the simulation layer, and GDScript will be used for the GUI and simulation visuals. The simulation layer will concern the input files, machine logic, simulation math, and output data. C# is ideal for this because it runs very fast compared to GDScript due to it being compiled JIT, whereas GDScript is interpreted.

GDScript will be used for the User Interface and graphics. Godot Script has convenient methods for UI elements which will allow us to call C# methods in the simulation layer. To link the C# simulation output data to the View and ViewModel layers, we can make use of signals⁴ in GDScript. We also plan to use JSON to store all configuration files such as the app settings file, machine recipe files, and results files.

7.2 Coding Conventions

In general, we will be following the Google Style Guide for C# .

Class names should be capitalized in PascalCase.

Local variables should be written in camelCase.

Variables and fields that can be made const should always be made const.

While comments are important, proper naming of variables and arguments is preferred to keep code self documenting.

Each method should have a comment immediately preceding it that explains what it does using the implied “This method…”, e.g. “Opens the file” instead of “Open the file”.  Any inputs / outputs should be listed, as well as whether the arguments can be null.

Variables should be named in a way that is descriptive enough to explain what they are used for.

Any complicated or tricky blocks of code should have a comment before them.

7.3 Code Version Control

We will be using Git and Github for version control. Godot lacks a built-in terminal similar to some other IDEs, so version control is managed from the system terminal. All Godot files are stored as text files, so the entire project including the Node hierarchy can be saved to Git.

Currently we are developing prototypes on a private Github repo, but eventually we will likely transition to using a repo primarily owned by the sponsor.
